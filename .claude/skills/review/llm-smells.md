# LLM Code Review Smells

Camada de [SKILL.md](SKILL.md) para código gerado ou fortemente assistido por LLM. O objetivo não é rejeitar código porque "parece IA", e sim achar pontos onde o autor pulou julgamento de engenharia.

Para diffs NestJS, aplicar junto com [nestjs-pass.md](nestjs-pass.md).

## Postura de review

Priorize bugs, segurança, gaps semânticos e testes ausentes. Smells de estilo são evidência para revisar mais fundo, não achados por si só.

- Segurança, vazamento de dado de paciente, autorização, race condition e quebra em produção → **blocker**.
- Smells de LLM → manutenibilidade, salvo quando escondem risco real.
- Cite arquivo/símbolo e o failure mode. Prefira "este caminho está ausente" a "isto poderia ficar mais limpo".

## Primeiro pass: smells de LLM

- Imports não usados; nomes genéricos (`data`, `result`, `item`, `temp`) onde caberia nome de domínio.
- **Helpers e funções auxiliares de uso único**, wrappers que só repassam, constantes usadas uma vez — o smell de LLM mais comum; reportar como **Obrigatório** (inline).
- Comentários inline narrando o código (`// save the patient`) — proibidos fora das exceções ([plexus-rules.md §2.1](../../rules/plexus-rules.md#21-comentários-inline)); JSDoc que só repete a assinatura sem dizer responsabilidade/erros.
- Service importando `typeorm`/`DataSource` "para resolver rápido" em vez de método no repository.
- `try { ... } catch (e) { throw e; }` ou `catch` amplo sem tradução, recuperação ou log útil.
- Cadeias `if/else`/`switch` onde um `Record<Enum, X>` ou mapa existente resolveria.
- Helper reinventado que já existe em `src/common/` ou no próprio módulo.
- Dependência nova em `package.json` sem necessidade clara (ou typosquat).
- Comentários mencionando ferramenta de IA ("generated by", "as suggested by Copilot").
- Estilo misto no arquivo: aspas, `async`/`.then`, forma de erro, naming diferentes do vizinho.
- Arquitetura genérica deslocada: interface + token + factory para uma implementação; repository que só repassa `find`; "service" de uma linha.
- Funções Frankenstein: blocos com nível de abstração ou vocabulário visivelmente diferentes.
- Tipos "para passar no compilador": `as any`, `as unknown as T`, `!` em sequência, `@ts-ignore`.
- Código para o happy path apenas: stream sempre começa com metadata, arquivo sempre cabe, banco nunca falha.

## Pass de segurança: obrigatório

Output de LLM costuma parecer seguro omitindo mitigações sutis. Sempre execute antes de aprovar.

### Injection

- Sem interpolação em `query()`, `createQueryBuilder().where(\`...${x}\`)`, `orderBy` com coluna vinda do cliente sem allowlist.
- Sem `child_process`, `eval`, `new Function`, `require` dinâmico com input externo.
- Path de arquivo nunca derivado de input (`fileName`) → path traversal.

### Autorização e IDOR

- Todo handler protegido verifica identidade (metadata `authorization`) **e** vínculo com o recurso.
- `findOneBy({ id })` vindo do cliente sem filtro de dono/escopo → IDOR.

### Vazamento de dados

- Resposta não devolve entity inteira, `disk_path`, notas em listagem.
- Logs sem CPF, nome, telefone, notas, chunk, token ([lgpd.md](lgpd.md)).
- Erros ao cliente sem stack, mensagem do driver `pg` ou path interno.

### Segredos

- Sem chave/token/senha hardcoded (inclui `appKey`/`appSecret` reais no `ObserveModule`).
- Segredo em código, teste, doc, log ou output → tratar como comprometido.

### Dependências

- Nova lib necessária, mantida, versionada no lockfile; preferir API do Nest/Node antes de adicionar pacote.
- `npm audit` quando o diff mexe em dependências ([security-hardening.md](security-hardening.md)).

### Concorrência e transações

- Writes multi-tabela num método atômico do repository (`DataSource.transaction` usando o `manager`).
- Unique sob concorrência (CPF) tratado — upsert ou captura de `23505`.
- Efeito fora do banco (mover arquivo, emitir evento) só após commit; compensação em falha.
- Detalhe: [concurrency-review.md](concurrency-review.md).

## Correção semântica e edge cases

- Erros explícitos; sem `catch {}` silencioso, sem Promise sem `await`/`catch`.
- Input externo: `undefined`, string vazia, buffer vazio, frames fora de ordem, duplicados, limites.
- Streaming: stream vazio, só metadata, metadata repetida, chunk antes de metadata, cancelamento, erro no meio.
- Tamanho: soma de chunks vs limite (100MB), `int64`/`bigint` tipado corretamente.
- Datas com `timestamptz`; nada de `new Date().toString()` como chave.
- Listagens com limite e ordenação estável.
- Testes cobrem o branch que falharia, não só o sucesso.
- Enum/status novo: grep de todos os usos do campo antes de aceitar a condição nova.
- Campo novo em mensagem proto: semântica do valor default (proto3 não distingue "ausente" de `""`/`0` sem `optional`) está tratada?

## Cobertura do invariante de negócio

Depois de validar o handler do diff, procure outros caminhos que escrevem na mesma entity/campo (outro handler, seed, script, rota HTTP) e confirme que a regra nova também vale lá. Ver [concurrency-review.md](concurrency-review.md) (Prioridade 4).

## Pass de performance

- Sem N+1 (relação carregada em loop, `findOne` por item).
- `save` em loop → `insert`/`save` em array.
- Arquivo inteiro em memória (`Buffer.concat` de chunks, `readFile` de arquivo grande) → stream.
- Listagem sem `take`.
- Detalhe: [typeorm-perf.md](typeorm-perf.md).

## Workflow

1. Entender o comportamento pretendido e o requisito.
2. Ler testes primeiro.
3. Pass de segurança antes de estilo.
4. Traçar auth da metadata até a query.
5. Edge cases semânticos (stream, tamanho, concorrência, dados grandes).
6. Performance e arquitetura só depois da correção estar clara.
7. Classificar: `Crítico` / `Obrigatório` / `Sugestão` / `Detalhe` (template em [SKILL.md](SKILL.md#template-de-output)).
